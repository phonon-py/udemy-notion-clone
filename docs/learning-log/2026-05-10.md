## 学んだこと

### 1. Controlled Component（制御コンポーネント）パターン

```tsx
<input
  value={name}
  onChange={(e) => setName(e.target.value)}
/>
```

- `value` と `onChange` をペアで使う
- **state が input の唯一の真実**になる構成
- 入力イベントが起きるたびに state を更新し、画面再描画で `value` が反映される

#### `(e) => ...` の `e` の正体

- React がイベントハンドラに自動で渡してくる**イベントオブジェクト**
- `e.target` = イベントを発火させた DOM 要素（この場合 `<input>`）
- `e.target.value` = その入力欄の**いまの値**
- 名前は慣習で `e`。`event` でも `evt` でもよい
- TypeScript では `React.ChangeEvent<HTMLInputElement>` 型が自動推論される

#### ❌ 引数を受け取らないと値が取れない

```tsx
onChange={() => setName("???")}  // 何が入力されたか分からない
```

### 2. `async/await` の深堀り

#### `async` の正体

「**この関数は Promise を返します**」という宣言。中で `await` が使える。

```tsx
const signup = async () => {  // ← 戻り値が Promise になる
    const { user, token } = await authRepository.signup(name, email, password);
};
```

#### `await` の正体

「**Promise の結果が出るまで一旦止まって待つ**」命令。`async` 関数の中だけで使える。

#### なぜ存在するか（背景）

- ネットワーク通信は時間がかかる（0.1 秒〜数秒）
- 「待ってる間にブラウザを固める」と最悪の UX になる
- そこで「結果は後で届く」という約束 (= **Promise**) を返して、メインスレッドは止めない仕組みになった

#### 古い書き方との対比（コールバック地獄 → `.then()` チェーン → `async/await`）

```ts
// .then() スタイル
api.login().then((res) => {
    api.getUser(res.id).then((user) => {
        api.getPosts(user.id).then((posts) => { /* ... */ });
    });
});

// async/await
const res = await api.login();
const user = await api.getUser(res.id);
const posts = await api.getPosts(user.id);
```

→ **同期コードのように上から下へ読める**のが最大の価値。

#### ⚠️ エラーハンドリング

`await` した処理が失敗すると例外が投げられる。本格的には `try/catch` でくるむ：

```tsx
try {
    const { user, token } = await authRepository.signup(...);
} catch (err) {
    console.error(err);
}
```

今日の Signup.tsx ではまだ未対応。講座が進むと追加されるはず。

### 3. JSX のネストデバッグ

補完が `</div>` を 1 つ余分に挿入したせいで、フォーム構造が崩れた事件。

#### 起きたこと

```
<div auth-form>
  <div>username</div>
  <div>email</div>
  <div>password</div>
</div>                ← ここで auth-form が早く閉じてしまった
<div>登録ボタン</div>  ← 本来は内側にいるべき
```

その後、修正中に逆方向に消しすぎて `</div>` 1 個不足になり、Vite oxc が `Unexpected token` エラーを返す状態になった。

#### 学んだ対処法

- **対応する閉じタグの色を VS Code が変えてくれる**（カーソルを開きタグに置く）
- **Prettier で整形すると、開閉が合わないとそもそも整形できない** → 早期発見できる
- **コンポーネントを切り出す**（`<UsernameField />` 化）と 1 ファイルあたりのネストが浅くなる

### 4. AI 補完との付き合い方

#### Gemini Code Assist の評価（調査結果）

| 観点 | 評価 |
| --- | --- |
| 補完精度 | Copilot 比 85〜90%。Cursor / Supermaven より下 |
| 速度 | 短文は Copilot が速い。長文・大規模文脈なら Gemini が強い |
| 信頼性 | 停止、レスポンスエラー、ハルシネーションの報告が多い |
| 無料枠 | 月 18 万回（Copilot Free の 90 倍）。コスト面は最強 |
| マルチファイル編集 | 未対応（Cursor / Claude Code に劣る） |

#### 結論：インライン補完を OFF に

- 思考のリズムが崩れる、自分で書きたい行を上書きされる、微妙にズレた提案を直すコスト > 自分で書くコスト
- METR の研究（2025-07）でも**経験者は AI 補完で 19% 遅くなる**との結果
- 学習中は特に「自分で書く経験」が定着に直結する → 補完オフが向く
- 業務では Claude Code（質問ベースの AI 支援）に一本化するのが合っている
