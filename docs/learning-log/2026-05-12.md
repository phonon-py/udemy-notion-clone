## 学んだこと

### 1. `try/catch/finally` の三段構え

```tsx
const signup = async () => {
    setIsSubmitting(true);
    try {
        const { user, token } = await authRepository.signup(name, email, password);
        setCurrentUser(user);
        localStorage.setItem('token', token);
    } catch (error) {
        console.error(error);
        alert('登録に失敗しました。入力内容を確認してください。');
    } finally {
        setIsSubmitting(false);
    }
};
```

#### 各ブロックの役割

| ブロック | 実行されるタイミング | 用途 |
| --- | --- | --- |
| `try` | 通常実行のメインロジック | 成功パスの処理 |
| `catch` | `try` の中で例外が投げられたとき | エラー処理 |
| `finally` | **成功・失敗どちらでも必ず実行** | クリーンアップ、ローディング解除など |

#### なぜ `finally` が必要か

`setIsSubmitting(false)` を `try` と `catch` の両方に書くと**重複**するし、片方に書き忘れる事故が起きやすい。`finally` に置けば 1 箇所で済む。

```tsx
// ❌ 冗長 & 書き忘れリスク
try {
    // 成功時
    setIsSubmitting(false);
} catch (e) {
    // 失敗時
    setIsSubmitting(false);  // 忘れると永久にボタン押せない
}

// ✅ finally で必ず実行
try { /* ... */ }
catch (e) { /* ... */ }
finally { setIsSubmitting(false); }
```

#### `catch` の引数の型

TypeScript 4.4 以降、`catch` の引数はデフォルトで `unknown` 型。`any` ではないので**いきなりプロパティにアクセスできない**：

```tsx
catch (error) {
    error.response.data.message;  // ❌ unknown 型なので不可
}
```

→ 型ガードを噛ます必要がある（次回以降のテーマ）：

```tsx
catch (error) {
    if (axios.isAxiosError(error)) {
        const message = error.response?.data?.message;
    }
}
```

### 2. `isSubmitting` パターン（多重送信防止）

```tsx
const [isSubmitting, setIsSubmitting] = useState(false);

const signup = async () => {
    setIsSubmitting(true);
    try { /* ... */ }
    finally { setIsSubmitting(false); }
};

<button disabled={!name || !email || !password || isSubmitting}>
    登録
</button>
```

#### なぜ必要か

ユーザーが登録ボタンを連打したらどうなるか？

- ❌ 同じユーザーを 2 回作ろうとして 2 回目以降は 400 エラー
- ❌ ネットが遅いと「押せてない？」と思ってさらに連打 → 状態がカオスに

**送信中は `isSubmitting = true`** にしてボタンを `disabled` にすれば、UI レベルで多重送信を防げる。

#### 重要：`finally` で必ず `false` に戻す

`try` の中で `setIsSubmitting(false)` を書いてしまうと、例外発生時に永久にボタンが押せなくなる。`finally` に置くのが鉄則。

### 3. `localStorage` への `token` 保存

```tsx
localStorage.setItem('token', token);
```

#### なぜ保存する必要があるか

- atom（Jotai）はメモリ上のデータ → **リロードすると消える**
- `localStorage` はブラウザのストレージ → **タブを閉じても残る**

これで「リロードしてもログイン状態が維持される」第一歩を踏んだ。

#### `localStorage` の特徴

| 観点 | 内容 |
| --- | --- |
| 永続性 | 明示的に削除するまで残る（プライベートウィンドウ閉じる、ユーザーが履歴削除など除く） |
| アクセス | 同一オリジン内の JavaScript から自由に読み書き可能 |
| 容量 | 5〜10MB 程度（ブラウザによる） |
| 値の型 | **文字列のみ**。オブジェクトは `JSON.stringify` 必須 |

#### ⚠️ セキュリティ上のトレードオフ

`localStorage` に token を保存する選択肢には**賛否両論**ある：

| 保存先 | メリット | デメリット |
| --- | --- | --- |
| `localStorage` | 実装が単純、SSR と相性◯ | **XSS で盗まれるリスク**（同オリジンの JS から自由に読める） |
| `sessionStorage` | タブを閉じれば消える | 同じく XSS で盗まれる |
| Cookie（HttpOnly） | JS からアクセス不可で XSS 耐性◎ | CSRF 対策が別途必要、設定が複雑 |
| メモリのみ（atom） | XSS でも漏れにくい | リロードで消える |

**個人学習の Notion クローンならリスク許容範囲**。本番の決済系などでは Cookie (HttpOnly) + SameSite が定石。

#### なぜ React state ではなく localStorage か

「ログイン状態の永続化」と「現在のセッション情報」は責務が違う：

- **`localStorage`** = サーバーへの再認証に使う「鍵」を持っておく場所
- **Jotai atom (`currentUserAtom`)** = アプリ稼働中の状態管理

両方使うのが普通の構成。次のステップでは「起動時に localStorage の token を使って自分のユーザー情報を取得 → atom にセット」という流れになるはず。

### 4. エラーの UI 表示は `alert` から

```tsx
alert('登録に失敗しました。入力内容を確認してください。');
```

`alert` はブラウザ標準のダイアログ。実装が一行で済むので**最初のステップとしては妥当**。

#### `alert` の限界

| 観点 | 評価 |
| --- | --- |
| 実装の楽さ | ◎ |
| デザインの統一性 | ❌ ブラウザネイティブの見た目で UI から浮く |
| 表示中の操作 | ❌ ブロッキング（他の操作が止まる） |
| アクセシビリティ | △ スクリーンリーダーで読まれ方が独特 |
| 細かい制御 | ❌ 閉じるまでの時間調整など不可 |

#### 次の段階：エラー文言を `useState` で持つ

```tsx
const [errorMessage, setErrorMessage] = useState('');

catch (error) {
    if (axios.isAxiosError(error)) {
        setErrorMessage(error.response?.data?.message ?? '登録に失敗しました');
    }
}

{errorMessage && <p className="auth-error">{errorMessage}</p>}
```

→ Controlled Component と同じ「**state で UI を制御する**」パターンの応用。
