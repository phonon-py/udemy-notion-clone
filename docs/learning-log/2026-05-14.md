## 学んだこと

### 1. `useEffect` を初めて実コードで使う

前回学んだ `useEffect` を App.tsx に組み込み：

```tsx
useEffect(() => {
    fetchCurrentUser();
}, []);

const fetchCurrentUser = async () => {
    try {
        const user = await authRepository.getCurrentUser();
        setCurrentUser(user);
    } catch (error) {
        console.error(error);
    } finally {
        setIsLoading(false);
    }
};
```

#### 何が起きているか

1. アプリ起動 → App コンポーネントが初回レンダー
2. `isLoading: true` なので `<div>Loading...</div>` が表示される
3. レンダー完了後に `useEffect` が走る → `fetchCurrentUser()` 実行
4. `/auth/me` に GET リクエスト（インターセプタが自動で token を付ける）
5. レスポンスから `User` を作って atom にセット
6. `setIsLoading(false)` でローディング解除
7. 再レンダー → Routes が表示される

→ これで**リロードしても token があれば自動で再ログイン状態になる**仕組みが完成。

#### 依存配列 `[]` の意味

「初回マウント時に **1 回だけ** 実行」を意味する。token から user を復元する処理は起動時に 1 回やればいいので、まさにこのパターン。

### 2. `getCurrentUser` の実装

```ts
async getCurrentUser(): Promise<User | undefined> {
    const result = await api.get("/auth/me");
    if (!result.data) return undefined;
    return new User(result.data);
}
```

#### 戻り値の型に注目

`Promise<User | undefined>` で、**ユーザーが取れない場合（ログアウト状態）も明示的に表現**している。

`null` ではなく `undefined` を選んでいる理由は TypeScript 文化的なもの：

- **`undefined`** = 「値がまだ無い」「未設定」を表すのに使われがち
- **`null`** = 「意図的に空をセットした」を表すのに使われがち

両方使えるが、講座は `undefined` 派。Jotai の atom 初期化が `atom<User>()`（=`undefined` 始まり）と合わせている。

### 3. axios のリクエストインターセプタ

#### なぜ必要か

これまでのコード：

```ts
// 仮に Note 取得 API を作る場合
const result = await api.get("/notes", {
    headers: { Authorization: `Bearer ${localStorage.getItem("token")}` }  // ❌ 毎回書く
});
```

→ **API を叩く全ての箇所で `Authorization` ヘッダを手書き**することになる。書き忘れも起きるし、保守も大変。

#### インターセプタとは

axios が**リクエストを送る前 / レスポンスを受け取った後**にフックを刺せる仕組み。

```ts
// src/lib/api/interceptors/request.ts
export const addAutorizationHeader = (
    config: InternalAxiosRequestConfig,
) => {
    const token = localStorage.getItem("token");
    if (!token) return config;
    config.headers.Authorization = `Bearer ${token}`;
    return config;
};
```

```ts
// src/lib/api/index.ts
api.interceptors.request.use(addAutorizationHeader);
```

→ これで**全ての axios リクエストに自動で token が付く**。アプリのどこから呼んでも書き忘れが起きない。

#### `InternalAxiosRequestConfig` 型

axios がリクエストを送るときの設定情報の型。`headers` / `method` / `url` / `data` などを持つ。

引数で受け取って、headers をいじって、return する。**「途中で加工して通す」**のがインターセプタの基本パターン。

#### 受け取った config を return する理由

axios のインターセプタは「**加工した config を return すると、その config でリクエストが送られる**」という約束。return しないと undefined が次に渡されて壊れる。

#### レスポンスインターセプタ（今日は未実装）

リクエスト側だけでなく、レスポンス側にも刺せる：

```ts
api.interceptors.response.use(
    (response) => response,
    (error) => {
        if (error.response?.status === 401) {
            // 401 ならログアウトして /signin に飛ばす、など
        }
        return Promise.reject(error);
    }
);
```

→ token 切れ（401）を全画面で一括処理する場面で活躍する。これは「残った疑問」に追加。

### 4. `Note` エンティティクラス

```ts
export class Note {
    id!: string;
    userId!: string;
    title?: string | null;
    content?: string | null;
    parentId?: number | null;
    createdAt!: Date;

    constructor(data: Note) {
        Object.assign(this, data);
        this.createdAt = new Date(data.createdAt);
    }
}
```

#### `id` と `userId` ── PK と FK の概念

- `id` = この Note 自身を識別する PK（DB 側で自動採番）
- `userId` = この Note を作ったユーザーの id を持つ **FK**（外部キー）

→ フロント側はあくまで「文字列の値」を持つだけで、DB の制約自体は API 側にある。

#### `title?: string | null` の二重表現

3 種類の「無い状態」を表現できる：

| 値 | 意味 |
| --- | --- |
| プロパティ自体が無い | `?` で許可（オブジェクトに `title` キーが存在しない） |
| `undefined` | `?` で許可 |
| `null` | `string \| null` で許可 |

DB の `NULL` 許容カラムを反映している（API が `null` を返す可能性がある）。

#### `parentId?: number | null` ── 階層構造の表現

Note が**親 Note を持てる**（=入れ子にできる）構造を示している。Notion のサイドバーで、ページの中にサブページがあるあの感じ。

- ルートのページ → `parentId` は `undefined` / `null`
- 子ページ → `parentId` に親ページの id が入る

これは「**自己参照リレーション**」と呼ばれる、ツリー構造の代表的なモデリング。

#### `constructor` 内で `Date` 変換する理由

```ts
constructor(data: Note) {
    Object.assign(this, data);
    this.createdAt = new Date(data.createdAt);
}
```

`Object.assign` の後にわざわざ `createdAt` を上書きしている。なぜか？

**API から返ってくる JSON では `createdAt` は文字列**（例: `"2026-05-14T07:53:00.000Z"`）。

JSON 自体は Date 型を持たないので、JSON.parse すると ISO 8601 形式の文字列になる。

```ts
// API レスポンスの状態
{ createdAt: "2026-05-14T07:53:00.000Z" }  // string

// Note クラスでは Date として扱いたい
note.createdAt.toLocaleString()  // "2026/5/14 16:53:00" のように表示したい
```

→ コンストラクタの中で `new Date(...)` を噛ませて、**Date オブジェクトに変換してから保持**する。これでフロント側のコードでは「`createdAt` は常に Date」という前提で書ける。

#### ❌ ダメな例：型注釈だけで安心しない

```ts
createdAt!: Date;  // 型は Date だけど…
// API からは "2026-05-14..." という文字列が来るので、
// このまま Object.assign すると実際は string が入っている（型の嘘）
```

→ TypeScript の型は**コンパイル時のチェックだけ**。実行時に値の型を保証するのは自分の責任。`new Date(...)` の変換が必須。

これは API レスポンス → ドメインモデル変換の典型パターンで、`User` クラスでも同じことが起きる可能性がある（`createdAt` を持つようになったら同じ対応が必要）。
