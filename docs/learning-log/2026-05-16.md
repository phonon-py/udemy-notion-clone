## 学んだこと

### 1. TypeScript の「オブジェクト型」と「関数型」を区別する

詰まったポイント。最初こう書いて構文エラーになった：

```ts
// ❌ 間違い
async create(params: (title?: string parentId?: number) => Promise<Note>) {
    ...
}
```

これは「params は『title と parentId を引数にとって Promise を返す**関数**』」と書いてしまっている。書きたかったのは「params は『title と parentId を持つ**オブジェクト**』」。

#### カッコの使い分け

| カッコ | 役割 |
| --- | --- |
| `( )` | 値の世界：関数呼び出し、関数定義の引数リスト |
| `{ }` | 値の世界：オブジェクトリテラル、関数本体 |
| `{ }` | **型の世界：オブジェクト型** |
| `( ) => ...` | **型の世界：関数型**（コールバックを引数で受けるとき） |

#### ❌ ダメな例 / ✅ 良い例

```ts
// ❌ 関数型として書いてしまった
params: (title?: string, parentId?: number) => Promise<Note>

// ✅ オブジェクト型
params: { title?: string; parentId?: number }
```

#### 戻り値の型は「メソッド側」に書く

戻り値の型注釈を引数の中に書いてしまっていたのも誤り。正しい場所はメソッドのパラメータリスト**直後**：

```ts
async create(params: { title?: string; parentId?: number }): Promise<Note> {
    //       引数の型はここに                              戻り値の型はここに
    ...
}
```

#### 関数型を書くのはどんな場面か（参考）

引数として**関数（コールバック）を受け取る**ときに使う：

```ts
function fetchAndProcess(callback: (data: Data) => void) {
    // ...
}
```

今回の Note 作成は「**オブジェクトを受け取って Promise を返す**」普通のメソッドなので、関数型は出る幕がなかった、というのが事の真相。

### 2. オブジェクトで引数を渡す設計の利点

```ts
// 呼び出し例
await noteRepository.create({ title: "新しいノート" });
await noteRepository.create({ title: "子ノート", parentId: 42 });
await noteRepository.create({});  // 両方省略も OK
```

#### なぜ「引数 1 個 1 個」じゃなく「オブジェクト 1 個」？

| 観点 | 引数 1 個 1 個 | オブジェクトで渡す |
| --- | --- | --- |
| 順番の覚えやすさ | 順番依存（間違えやすい） | 名前で渡すので順番自由 |
| 後から項目を増やしたとき | 全呼び出し側を書き換える必要あり | 既存の呼び出しはそのままで OK |
| 省略可能なものとの相性 | 末尾しか省略できない | どこでも省略可能 |
| 読みやすさ | 何を渡してるか分かりにくい | キー名で明示される |

特に**省略可能な項目があるとき**は、オブジェクト渡しが定石。

### 3. Home ページのノート作成機能

これまでの認証フォームで使ったパターンを Home ページに応用：

```tsx
const [title, setTitle] = useState('');
const [isSubmitting, setIsSubmitting] = useState(false);

const createNote = async () => {
    setIsSubmitting(true);
    try {
        const newNote = await noteRepository.create({ title });
        setTitle('');
        console.log('Created note:', newNote);
    } catch (error) {
        console.error('Failed to create note:', error);
        alert('ノートの作成に失敗しました。もう一度試してください。');
    } finally {
        setIsSubmitting(false);
    }
};
```

**Signup / Signin と全く同じ構造**：

- `useState` で入力値を管理（Controlled Component）
- `useState` で `isSubmitting` を持って多重送信防止
- `try/catch/finally` で API エラー処理
- 成功時は state をクリア（`setTitle('')`）

→ **同じパターンを別の場面で再利用できる**ことを体験。React で「データを送信するフォーム」は、ほぼこの形に収束する。

#### `{ title }` のショートハンド

```ts
await noteRepository.create({ title });
// ↑ これは下と同じ意味
await noteRepository.create({ title: title });
```

オブジェクトリテラルで「キー名と変数名が同じ」なら省略できる**プロパティショートハンド**。React コードで頻出。

#### 成功時に state をクリアする理由

```ts
const newNote = await noteRepository.create({ title });
setTitle('');  // ← 入力欄を空に戻す
```

ユーザー視点では「作成ボタンを押した → 作られた → 次のノートを入力したい」という流れ。入力欄を空に戻さないと、前のタイトルが残ったままになって UX が悪い。

### 4. 補完事故：`try` が `true` に化けた

今日いちばんやらかしたミス。

```ts
// 起きていたコード
setIsSubmitting(true);
true {                  // ← ここが trueになっていた
    const newNote = await noteRepository.create({ title });
    ...
} catch (error) {       // 孤立した catch
```

#### 何が起きたか

- `tr` と打って、候補に `true` が出た
- そのまま Tab / Enter で確定 → `try` のつもりが `true` に
- 真偽値リテラルの後に `{` が続く意味不明な並び → パースエラー
- 下にある `catch` / `finally` も「対応する `try` がない」ので連鎖的にエラー

#### 教訓

- **`try/catch/finally` の枠を**先に全部書いてから中身を埋める**と、こういう事故が減る
- `try` / `true` / `throw` のような 3〜4 文字の似たキーワードは補完が暴走しやすい
- 「動かない」と思ったら、まずは IDE のエラー位置から数行**上に遡って**みるのが鉄則
