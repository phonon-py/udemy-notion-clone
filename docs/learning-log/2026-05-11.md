## 学んだこと

### 1. Jotai による状態のグローバル管理

#### 何のために導入したか

「ログイン中のユーザー情報」を**複数のコンポーネントから読み書きしたい**。

- `Signup` / `Signin` → 認証成功時にユーザーをセット
- `Layout` → 未ログインなら `/signin` に飛ばすために読む

これを `useState` だけでやろうとすると、**props を何階層もバケツリレー**することになる（prop drilling）。Jotai はそれを避けるための**グローバル状態管理ライブラリ**。

#### atom の定義

```ts
// src/modules/auth/current-user.state.ts
import { atom } from "jotai";
import { User } from "../users/user.entity";

export const currentUserAtom = atom<User>();
```

- `atom<User>()` で「中身が User 型の atom」を 1 つ作る
- 初期値を渡していないので `undefined` スタート

#### 使い方の対比

| 用途 | フック | 戻り値 |
| --- | --- | --- |
| 読み書き両方したい | `useAtom(atom)` | `[value, setValue]` — `useState` と同じ形 |
| 読むだけ | `useAtomValue(atom)` | `value` |
| 書くだけ | `useSetAtom(atom)` | `setValue` |

```tsx
// Signup / Signin（書き込みも読み込みも）
const [currentUser, setCurrentUser] = useAtom(currentUserAtom);

// Layout（読むだけ）
const currentUser = useAtomValue(currentUserAtom);
```

→ **使う側に応じて適切なフックを選ぶ**ことで、不要な再レンダーを避けられる（読むだけのコンポーネントを Setter の変更で再描画させない）。

#### なぜ Redux ではなく Jotai？（歴史的経緯）

- **Redux**: 中央集権・action / reducer 設計。学習コスト高、ボイラープレート多
- **Recoil（Meta 製、開発停止傾向）**: atom ベースで Jotai と思想が近い
- **Jotai**: 「もっとシンプルに atom だけで十分じゃない？」をやり切った後継。React 19 とも相性が良い

講座が Jotai を選んでいるのは、**学習コストの低さと現代的なシンプルさ**のため。

### 2. サインイン機能の実装

`Signup` で身につけた **Controlled Component + async/await** のパターンを `Signin` に応用：

```tsx
const [email, setEmail] = useState('');
const [password, setPassword] = useState('');
const [currentUser, setCurrentUser] = useAtom(currentUserAtom);

const signin = async () => {
    const { user, token } = await authRepository.signin(email, password);
    setCurrentUser(user);  // ← Jotai の atom にユーザーをセット
};
```

`authRepository` 側にも `signin` メソッドを追加。`signup` と同じ「レスポンスを `new User(...)` でラップして返す」設計に揃えている：

```ts
async signin(email, password): Promise<{ user: User, token: string }> {
    const result = await api.post("/auth/signin", { email, password });
    const { user, token } = result.data;
    return { user: new User(user), token };
}
```

→ **同じ形のインターフェースに揃える**ことで、呼び出し側のコードが一貫する。

### 3. 認証ガード（`<Navigate>` でのリダイレクト）

react-router-dom v6+ では、**条件によって別のルートへ飛ばすときは `<Navigate>` コンポーネントを返す**のが定石。

#### Layout 側：未ログインなら `/signin` へ

```tsx
const currentUser = useAtomValue(currentUserAtom);
if (!currentUser) return <Navigate to="/signin" replace />;
```

- `replace` を付けると履歴を**置き換える**（戻るボタンで戻れなくなる）→ ログイン画面に飛ばした後、ブラウザの戻るで保護ページに戻れないようにする狙い

#### Signin / Signup 側：ログイン済みなら `/` へ

```tsx
if (currentUser) return <Navigate to="/" replace />;
```

→ 既にログインしているユーザーがサインイン画面に来た場合、ホームに戻す。

#### ❌ よくある誤解：早期 return は hook より後ろに

```tsx
// ❌ こう書くと React の Rules of Hooks 違反になる
if (!currentUser) return <Navigate to="/signin" />;
const [x, setX] = useState(0);  // hooks が条件付きで呼ばれる
```

→ **hooks は必ず関数の先頭でまとめて呼ぶ**。条件分岐や return は hook 呼び出しの後。

### 4. API エラー（400）のデバッグ手順

#### 起きたこと

`Signup` 送信時に：

```
Uncaught (in promise) AxiosError: Request failed with status code 400
```

#### 400 ステータスだけでは原因不明

400 = 「リクエストに何か問題あり」という汎用ステータス。**レスポンスボディ**を見ないと中身が分からない。

#### 確認手順

1. DevTools → **Network タブ** → `/auth/signup` のリクエストを選択
2. **Response タブ**を確認 → `{"message": "このメールアドレスは既に使用されています"}`

→ 原因はメアド重複と判明。別アドレスで再試行して成功を確認。

#### 恒久対策（次回以降）

```tsx
const signup = async () => {
    try {
        const { user, token } = await authRepository.signup(name, email, password);
        setCurrentUser(user);
    } catch (err) {
        if (axios.isAxiosError(err)) {
            const message = err.response?.data?.message ?? "登録に失敗しました";
            setErrorMessage(message);  // useState で管理してUI表示
        }
    }
};
```

### 5. Error Boundary（エラー境界）と `try/catch` の使い分け

#### React が出した警告

```
An error occurred in the <Signup> component.
Consider adding an error boundary to your tree...
```

→ AxiosError が誰にもキャッチされず、コンポーネントツリーまで伝播したのが原因。

#### ErrorBoundary とは

コンポーネントツリーの中で起きたエラーを**ここで止めて**、フォールバック UI を出す仕組み。

#### ⚠️ ErrorBoundary の守備範囲には限界がある

| 場所 | ErrorBoundary が捕まえる？ |
| --- | --- |
| レンダー中の例外 | ✅ |
| ライフサイクルメソッド内のエラー | ✅ |
| **イベントハンドラ内のエラー（今回のケース）** | ❌ |
| **非同期処理（Promise、setTimeout）のエラー** | ❌ |

→ **`onClick` で発火する `async signup` のエラーは ErrorBoundary では拾えない**。`try/catch` が必須。

#### 使い分け表

| 概念 | 役割 | 今回必要か |
| --- | --- | --- |
| `try/catch` | イベントハンドラ・async 関数内のエラーを受ける | ✅ 今回はこっち |
| ErrorBoundary | レンダー中の予期せぬエラーで画面が真っ白になるのを防ぐ | 将来的に入れるとよい |
